# SQLShield — SQL Injection Detection & Security Monitoring System

> **SQLShield** is a full-stack security monitoring system designed to detect, analyze, block, and visualize SQL injection attacks in real time.
> The platform combines SQL injection detection middleware, authentication, role-based capability control, PostgreSQL event storage, administrative monitoring, analytics, and Docker-based deployment.

---

## 📌 Project Overview

SQL injection remains one of the most dangerous web application security vulnerabilities because improperly handled user input can be manipulated to alter database queries, bypass authentication, expose sensitive information, or modify application data.

**SQLShield** was developed as a defensive security system that demonstrates how a web application can:

* Detect suspicious SQL injection patterns.
* Assign risk scores to potentially malicious requests.
* Classify detected attacks by severity.
* Block malicious requests.
* Record security events in PostgreSQL.
* Monitor attacking IP addresses.
* Provide administrators with real-time security information.
* Display attack statistics and trends.
* Analyze attack severity and categories.
* Protect administrative endpoints through authentication and capabilities.
* Run consistently through Docker containers.
* Deploy to an Ubuntu AWS EC2 server.

The project has evolved from a basic SQL injection detection concept into a complete security monitoring platform where the **Attack Monitor displays real security events generated by actual requests rather than static demonstration data**.

# ✨ Main Features

## 1. SQL Injection Detection

SQLShield analyzes incoming request data for suspicious SQL injection patterns.

Examples of suspicious characteristics include:

* Boolean-based SQL injection patterns.
* SQL comments.
* Authentication bypass patterns.
* Suspicious SQL operators.
* Malicious query fragments.
* Common SQL injection syntax.

Detected requests can be assigned a risk score and severity level.

---

# 🚨 Risk Scoring

The system uses a risk score to represent the potential threat level of a request.

The project uses risk categories such as:

| Risk Score | Classification |
| ---------: | -------------- |
|       0–39 | Low            |
|      40–69 | Medium         |
|      70–89 | High           |
|     90–100 | Critical       |

Risk scoring allows security events to be prioritized.

For example:

```text
Risk Score: 80
Severity: CRITICAL
Blocked: TRUE
```

The exact score depends on the detection rules triggered by the request.

---

# 🔥 Attack Severity

SQLShield categorizes security events according to severity.

Typical classifications include:

* `LOW`
* `MEDIUM`
* `HIGH`
* `CRITICAL`

This allows administrators to quickly identify the most dangerous activity.

---

# 🚫 Request Blocking

When a request is identified as malicious according to the configured detection rules, SQLShield can block the request instead of allowing it to continue through the application.

A blocked security event can contain information such as:

```text
IP Address
Endpoint
HTTP Method
Payload
Attack Type
Severity
Risk Score
Blocked Status
Timestamp
```

This provides both prevention and forensic information.

# 📡 Real-Time Attack Monitoring

One of the major features of the project is the **Attack Monitor**.

The Attack Monitor does not rely on hard-coded demonstration data.

Instead, it retrieves security events from the PostgreSQL `security_events` table.

The monitoring system can display information such as:

* Attacking IP address.
* Target endpoint.
* Attack type.
* Severity.
* Risk score.
* Blocked status.
* Timestamp.

Example:

```text
IP Address       105.x.x.x
Endpoint         /api/v1/auth/login
Attack Type      SQL Injection
Severity         CRITICAL
Risk Score       80
Blocked          TRUE
```

This allows the dashboard to represent actual activity generated against the application.

# 🧩 Role-Based Capability System

SQLShield implements capability-based authorization for administrative functionality.

Instead of relying only on a user's role name, administrative access can be associated with specific capabilities.

Example capabilities include:

```text
VIEW_USERS
CREATE_USERS
DELETE_USERS
VIEW_SECURITY_EVENTS
MANAGE_SYSTEM
VIEW_DASHBOARD
MANAGE_USERS
```

For example:

```text
Role: admin

Capabilities:

VIEW_USERS
CREATE_USERS
DELETE_USERS
VIEW_SECURITY_EVENTS
MANAGE_SYSTEM
VIEW_DASHBOARD
MANAGE_USERS
```

This provides a more granular authorization model.

---

# 🛂 Capability Middleware

Administrative routes can require a specific capability.

For example:

```text
GET /api/v1/admin/dashboard
```

can require:

```text
VIEW_DASHBOARD
```

The authorization flow becomes:

```text
JWT
 ↓
Authenticated User
 ↓
User Role
 ↓
Capability Lookup
 ↓
Required Capability
 ↓
Allow / Deny
```

This prevents users from accessing administrative functionality simply by knowing the endpoint.

# 🛡️ SQL Injection Protection

The project uses multiple defensive layers.

## Input Validation

Authentication input is validated before reaching the application logic.

For example, login email input uses email validation.

## Parameterized Database Queries

Database queries should use parameterized statements rather than concatenating user-controlled input into SQL.

Example:

```javascript
const result = await pool.query(
    `
    SELECT *
    FROM users
    WHERE email = $1
    `,
    [email]
);
```

This is safer than dynamically constructing SQL using raw user input.

## Detection Middleware

SQLShield additionally inspects requests for suspicious injection patterns.

## Rate Limiting

Rate limiting helps reduce repeated automated requests.

## Security Headers

HTTP security headers are applied through the application's security middleware.


## Dashboard returns 500

Inspect:

```bash
docker compose logs backend --tail=100
```

Database schema mismatches can cause backend queries to fail.

For example, if application code expects:

```text
risk_score
```

but the database table does not contain that column, PostgreSQL will return an error.

The application queries and database schema must remain synchronized.


# ⚠️ Limitations

SQLShield is a defensive demonstration and monitoring system.

Its SQL injection detection is based on configured detection rules and should not be considered a replacement for secure application development.

The strongest protection against SQL injection remains:

1. Parameterized queries.
2. Proper input validation.
3. Least-privilege database accounts.
4. Secure ORM/database usage.
5. Appropriate authorization.
6. Regular security testing.

SQLShield adds another defensive layer by detecting and monitoring suspicious activity.

Rather than treating SQL injection as only a database problem, the project approaches it as a complete security-monitoring problem:

```text
             DETECT
                ↓
             ANALYZE
                ↓
              SCORE
                ↓
             CLASSIFY
                ↓
              BLOCK
                ↓
              LOG
                ↓
             MONITOR
                ↓
             ANALYZE
                ↓
            RESPOND
```

The result is a practical security platform that combines application security, backend development, database engineering, authentication, authorization, monitoring, analytics, containerization, and cloud deployment into a single project.

**SQLShield — Detect. Protect. Monitor. Analyze.**
